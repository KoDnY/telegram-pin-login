## User Scenarios & Testing *(mandatory)*

### User Story 1 - Вход и просмотр своего профиля (Priority: P1)

Пользователь открывает отдельное приложение на компьютере, переходит по ссылке в Telegram-бота, получает PIN командой /start, вводит его в приложении и видит свой профиль.

**Why this priority**: Это основной сценарий задания, демонстрирующий запрос, обработку на сервере и ответ клиенту.

**Independent Test**: Пройти сценарий от окна входа до отображения профиля с действующим PIN.

**Acceptance Scenarios**:

1. **Given** приложение открыто, **When** пользователь находится в окне входа, **Then** доступны поле PIN, кнопка входа и ссылка на бота.
2. **Given** пользователь отправил /start, **When** запрос обработан, **Then** бот показывает шестизначный PIN, связанный с этим пользователем.
3. **Given** PIN не использован и с момента выдачи прошло менее 15 минут, **When** пользователь вводит его и нажимает кнопку входа, **Then** сервер возвращает профиль соответствующего пользователя, а приложение открывает главное окно.
4. **Given** вход выполнен и данные доступны в Telegram, **When** показано главное окно, **Then** отображаются имя, фамилия, username и аватар пользователя.

### User Story 2 - Контроль срока и повторного использования PIN (Priority: P1)

Пользователь может запросить новый PIN; старый код после этого больше не позволяет войти.

**Why this priority**: Срок действия и одноразовость являются явными условиями задания пользователя.

**Independent Test**: Проверить вход с использованным, просроченным и заменённым PIN отдельно от интерфейса профиля.

**Acceptance Scenarios**:

1. **Given** PIN уже использован для успешного входа, **When** его отправляют повторно, **Then** вход не выполняется.
2. **Given** с выдачи PIN прошло 15 минут или больше, **When** его отправляют для входа, **Then** вход не выполняется.
3. **Given** у пользователя есть действующий PIN, **When** он повторно отправляет /start, **Then** получает новый PIN, а предыдущий немедленно теряет силу.
4. **Given** код не соответствует ни одному действующему PIN, **When** выполнена попытка входа, **Then** профиль не возвращается и главное окно не открывается.

### User Story 3 - Проверка доступности сервера (Priority: P2)

Демонстратор проверяет, что сервер принимает запрос и возвращает статус доступности без предварительного входа.

**Why this priority**: Проверка доступности отдельно указана в исходном ТЗ.

**Independent Test**: Отправить запрос проверки доступности работающему серверу и получить успешный статус.

**Acceptance Scenarios**:

1. **Given** сервер работает, **When** отправлен запрос проверки доступности, **Then** получен успешный статус.

### User Story 4 - Сообщение администратору (Priority: P2)

После входа пользователь открывает окно отправки сообщения, вводит текст и отправляет его администратору в Telegram.

**Why this priority**: Пользователь согласовал дополнительную демонстрацию передачи данных после входа.

**Independent Test**: Войти, отправить текст из приложения и проверить его получение администратором в Telegram.

**Acceptance Scenarios**:

1. **Given** пользователь вошёл и получатель настроен, **When** он отправляет текст, **Then** сообщение проходит через сервер и поступает администратору в Telegram.
2. **Given** отправка завершилась успешно, **When** приложение получает результат, **Then** пользователь видит подтверждение отправки.
3. **Given** отправка завершилась ошибкой, **When** приложение получает результат ошибки, **Then** пользователь видит ошибку, а не подтверждение успеха.
4. **Given** администратор отвечает в Telegram, **When** пользователь смотрит приложение, **Then** ответ не отображается: обратная доставка исключена из первой версии.

### Edge Cases

- Использованный, истёкший, заменённый и неизвестный PIN: вход отклоняется.
- Граница срока: по достижении 15 минут код недействителен.
- Одновременные попытки использовать один PIN: успешное использование возможно только один раз.
- Несколько пользователей: введённый PIN должен возвращать профиль именно связанного с ним пользователя.
- Отсутствие фамилии, username или аватара; недоступность сети; ввод не из шести цифр: конкретное отображение и сообщения пока не согласованы, дополнительных требований к ним не установлено.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Клиент должен быть отдельным приложением на компьютере; встраивание внутрь Telegram не входит в согласованный объём.
- **FR-002**: Окно входа должно содержать поле PIN, кнопку входа и ссылку на Telegram-бота.
- **FR-003**: Команда /start должна приводить к выдаче пользователю PIN из шести цифр.
- **FR-004**: Выданный PIN должен быть связан с данными конкретного Telegram-пользователя, переданными серверу ботом.
- **FR-005**: Клиент должен отправлять введённый PIN серверу для проверки; решение об успешном входе принимает сервер.
- **FR-006**: PIN должен действовать 15 минут с момента выдачи и становиться недействительным после одного успешного входа.
- **FR-007**: Повторная команда /start должна выдавать новый PIN и немедленно отменять предыдущий PIN этого пользователя.
- **FR-008**: После успешной проверки сервер должен возвращать профиль пользователя; клиент должен показывать имя, фамилию, username и аватар при наличии этих данных.
- **FR-009**: Недействительный PIN не должен предоставлять доступ к профилю.
- **FR-010**: Сервер должен предоставлять проверку доступности с возвратом статуса.
- **FR-011**: После входа пользователь должен иметь окно ввода текста и действие отправки сообщения администратору.
- **FR-012**: Сообщение должно передаваться через сервер администратору в Telegram.
- **FR-013**: Приложение должно показывать результат отправки: успех или ошибку.
- **FR-014**: Обратная доставка ответов администратора в приложение не входит в первую версию.

### Key Entities

- **Пользователь**: участник входа, идентифицируемый по Telegram; профиль включает имя, фамилию, username и аватар, если они доступны.
- **PIN**: шестизначный код, связанный с пользователем; имеет момент выдачи, срок действия и факт использования или отмены.

- **Сообщение администратору**: текст, отправленный вошедшим пользователем через сервер назначенному получателю в Telegram.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Полный демонстрационный сценарий от /start до профиля завершается успешно с действующим PIN.
- **SC-002**: Каждая из четырёх контрольных попыток с использованным, просроченным, заменённым и неизвестным кодом отклоняется.
- **SC-003**: При проверке двумя разными пользователями каждый из двух действующих кодов возвращает профиль своего владельца.
- **SC-004**: Код работает до истечения 15 минут и не работает на границе срока и после неё.
- **SC-005**: Проверка доступности работающего сервера возвращает успешный статус без входа.

- **SC-006**: Отправленный в демонстрации текст получен администратором в Telegram, а приложение показывает успешную отправку.
- **SC-007**: При имитации ошибки доставки приложение показывает ошибку и не сообщает об успехе.

## Assumptions

Новые продуктовые требования по умолчанию не добавляются: пользователь запросил предварительные вопросы.

- Для демонстрации необходимы Telegram-аккаунт, настроенный бот, работающие компоненты и доступ к сети.
- База данных исключена пользователем. Хранение в памяти и потеря временных данных при перезапуске ранее предложены ассистентом; это пока проектное предложение, а не отдельное согласованное требование.
- Сохранение входа между запусками, дополнительные роли доступа и дополнительные пользовательские данные не входят в подтверждённые требования.
- Численные требования к скорости, нагрузке и длительности пользовательского сценария не заданы и не вводятся самостоятельно.
- Технические ограничения пользователя сохранены отдельно в constraints.md для последующего планирования.

## Clarifications

- Пользователь выбрал вариант А: односторонняя отправка сообщений администратору в первой версии с отображением результата отправки.
- Конкретный получатель в Telegram и способ его настройки определяются при планировании и настройке запуска; это не требует добавления новых пользовательских функций.
